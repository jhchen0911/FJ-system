請款單單筆在 iPhone 停在舊版：程式調查（唯讀，origin/main 5fb6b52，v6.0.176）

結論一句話：請款單是「整筆、修改時間（_mt）新者勝，同分時本機勝」，沒有三方合併；只要 iPhone 那份的 _mt ≥ 雲端那份， 每次下載都會「保留本機」，而且下載後把本機那份當成新的同步基準（所以不會自動上傳、雲端也不會被蓋，兩邊就永遠各留一份）。 最大風險：iPhone 只要碰到這張單（打開編輯、開該案工程專案頁觸發自動結算…），舊版就會帶著新的 _mt 上傳，蓋掉雲端正確版。

2. 可能原因（依可能性排序）

A（最可能）iPhone 那份被「被動」改過、_mt 變新，但沒有上傳成功／沒標成待上傳，之後下載時本機勝、基準被重設。

  • 開機或渲染時會自動改請款單並 _touch 的路徑：_autoSettle L34244（renderProj L32103 開工程專案頁就跑；改 contractQty→_recalcInvAmounts→_touch，L34269）、_invAfterLoad L5239／_invSyncUntouched L5137、loadInvoice L2875（日期空白就填今天並 _touch）、報價改名連動 L2018、付款規則同步 L4078、recalcAllExpected L29235。
  • 沒被標待上傳的縫：_autoUpload L21086 未登入（_fbUser 還沒好）就直接 return，連 _markDirty 都不做；套用雲端期間 _applyingCloud 也不標。接著登入→不 dirty→_applyCloudSnapshot→本機 _mt 較新勝出→基準改成本機版（且基準是在 _pullPrivate 回呼後才寫，L11057，中間的本機變動也一起被吞進基準）→永不上傳。
  • 或上傳一直失敗（舊版被 _verGuard、員工帳號整包 update 被規則拒、_syncDropGuard 擋自動上傳）：頂欄會一直顯示橘色「未同步」，每次合併仍是本機勝。

B 電腦那次修改的 _mt 比 iPhone 那份小：saveInvoice 用電腦時鐘 Date.now()，若電腦時間偏慢、iPhone 那份是用伺服器時間戳的，電腦的新版反而「比較舊」。

C 電腦改了內容卻沒升 _mt（同分→本機勝）：查過能改 date／totals 的路徑（saveInvoice、autoSaveInv L3912、_recalcInvAmounts 的各呼叫點、confirmReceipt、_erdMigrate、recalcAllExpected）都有升 _mt；只找到 migrateInvQuoteIds L4267（每次 renderInvList 都跑）改 quoteId 不升 _mt，改不到日期與金額 → 對本案可能性低，但違反規則 4。

D iPhone 根本沒下載到那次更新：下載條件比的是「雲端 uploadedAt（上傳裝置的時鐘）」vs「iPhone 的 fy_last_fb_sync（自己上傳時用 iPhone 時鐘）」。iPhone 時鐘偏快時會漏拉，但之後電腦再上傳一次就會整份下載、靠 _mt 合併——只會暫時落後，不會長期只差一筆 → 低。

E 其實是兩筆不同 id（重複單）：iPhone 有一張沒上傳成功的草稿、電腦是另一張 → 看兩邊請款單張數是否一樣即可排除。

怎麼分辨（看 iPhone 那份的 _mt／_by）：iPhone 沒有顯示 _mt 的畫面，但可以在 iPhone 做「匯出備份」（exportData L7626，JSON 含每張請款單 _mt、_by、devId、appVersion），和電腦匯出（或 Firebase 主控台 fydata/shared/invoices/<id>/_mt）比：

  • iPhone _mt > 雲端 → A 或 B（_by 是誰、時間點在電腦修改之後 → A；_mt 在未來或兩台時鐘差很多 → B）
  • 兩邊 _mt 相同、內容不同 → C
  • iPhone _mt < 雲端 → D（看 fy_last_fb_sync）
  • 張數不同 → E
  • 另看頂欄有沒有橘色「未同步」：有 → 上傳一直失敗那一支。

3. 最大風險：iPhone 下次存檔會不會把舊版蓋回雲端？

會，條件是這張單在 iPhone 上被改到（hash 變了）。 只有 hash 和基準不同的那筆會上傳；上傳前就算有先合併，本機 _mt 較新照樣勝出，然後 update() 直接寫進雲端（規則不比 _mt）。 會觸發的動作：在 iPhone 打開這張請款單（日期空白→loadInvoice 自動填今天＋_touch；之後任何一次 saveInv／失焦自動存檔就會帶著舊明細＋今天的日期上傳）、開這個案子的工程專案頁（_autoSettle）、在 iPhone 改報價名稱／付款規則／重算收款日、登錄收款、fy_rec_hashes 遺失。 只看列表、不碰這張單 → 不會上傳（基準＝舊版，hash 沒變）。

4. 安全的修復步驟（不用改程式）

建議方法（最穩）：

  1. iPhone 先不要點開這張請款單、也不要開這個案子的工程專案頁。
  2. 在電腦打開這張請款單 → 不用改任何東西，直接按「儲存」（_mt 變成現在；已鎖住的期別金額沒變也能存）。等頂欄沒有「未同步」。
  3. iPhone 切到別的 App 再切回來（或重新整理），會自動下載；確認這張變成 670,143.6、請款日 2026-09-01。
  4. 如果第 3 步沒變：表示 iPhone 那份 _mt 在未來（時鐘問題）→ 用備用方法。

備用方法（整台重新下載）：先確認 iPhone 頂欄沒有「未同步」（有就代表還有沒上傳的東西，先別做）→ Safari「設定 › Safari › 進階 › 網站資料」刪除 jhchen0911.github.io（加到主畫面的 App 就是刪掉 App 重新加入）→ 重新開啟、登入，整份從雲端下載。 不要做：只刪 fy_inv 一個鍵（基準還在，下次上傳會把雲端請款單全部當成「本機已刪」送 null；雖有筆數暴跌保護，風險仍高）；不要按「從雲端下載」期待它覆蓋（它一樣是新者勝）。

需要改程式（建議下一批 hotfix）：

  1. 把 invoices 加進 _CF_COLLS（L40212）。_recMerge3 L40278 已經有「本機自上次同步後沒改過 → 用雲端版，不管 _mt」（if(!lc.length)return cloud;）＝每台裝置的 dirty 判斷，正好治這個病；同欄位兩邊都改才進「同步衝突」清單（_CF_COLL_NAME L40328 要補「請款單」）。注意 items 是一整個欄位比對、請款單比較大，要量一下 fy_rec_base 大小。
  2. saveInvoice L3880 改用 _touch（伺服器時間），與其他路徑一致。
  3. 被動重算（_autoSettle、loadInvoice 填今天、_invAfterLoad）內容沒變不戳 _mt（照 v5.441 _recSame 原則）；loadInvoice 的「日期空白填今天」只填畫面、按儲存才寫回。
  4. migrateInvQuoteIds L4267 改了要 _touch（規則 4）。
  5. _applyCloudSnapshot 的逐筆基準改用「這次收到的雲端版」而不是「合併後的本機」，本機勝出且內容不同的那幾筆改標待上傳或列出來（見第 5 點），不要靜默吞掉。

5. 提案：「這台和雲端同一筆不一樣」健檢（不加按鈕）

  • 本機端（第一步，不用改規則）：每次 _applyCloud 合併 _REC_COLLS 時，記下「雲端版和本機版內容不同、結果卻留本機」的記錄（id、集合、兩邊 _mt、兩邊金額摘要、本機自上次同步後有沒有改過＝本機 hash 是否等於 fy_rec_hashes 基準），存本機 fy_sync_div。
  • 資料健檢（_healthRows L35389 再加一列）顯示「這台有 N 筆和雲端不同」，逐筆寫名稱、期別、本機／雲端金額與修改時間。
  • 首頁待辦（_v6TodoItems）出一張卡，點進去用既有的「同步衝突」視窗（openSyncConflicts）選要哪一版——不新增按鈕。
  • 「本機沒改過卻比雲端新」的那種直接改用雲端（等同第 4 點的修正 1），健檢只記一筆紀錄。
  • 跨裝置（第二步，要發布規則）：每台裝置上傳時順便寫 fydata/syncCheck/<裝置id>＝{at, ver, by, h:{invoices:{id:hash}, quotes:{…}}}（djb2 hash 很小，200 案約數 KB）。管理員裝置的健檢讀全部裝置，和雲端 hash 比，列出「某台裝置的某筆和雲端不同、最後同步時間」——老闆娘的手機有沒有停在舊版，在電腦上就看得到。
