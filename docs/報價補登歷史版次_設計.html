3.3 套用時做的事（技術）

做法核心：把更正寫成一條「規則」存在報價記錄上，每台裝置自己照規則改，而不是只改本機那幾筆紀錄。

q.verFix = [{
  id: 'vf_115102501_v2',                 // 冪等鍵：已存在就不再做
  at, by,                                // 套用時間、管理員 email
  insert: { savedAt: SRC.savedAt + 1,    // 新正式版的身分（不能跟來源同一個 savedAt，見風險 3）
            src: SRC.savedAt, ver: 2,
            date: '2026-10-27',
            note: '送出 PDF 115/10/27（補登 115/11/0X）' },
  shiftFrom: SRC.savedAt,                // savedAt 晚於這個、ver ≥ 2 的正式版次一律 +1
  verTo: 4,                              // q.ver 至少要是這個（現行 3 → 4）
  before: { qVer: 3, entries: [{savedAt, ver, snapVer}], rfqs: {rid: quoteVer}, chg: {...}, invs: {invId: quoteVer} },
  undone: false
}]

套用步驟（_qvfApply，全部在一次存檔內完成）：

  1. 備份（任何一步失敗就整個取消）
  2. 下載一個 JSON：{q, Q_HISTORY[qid], qHistSens[qid], 相關請款單, 草稿}，檔名 補登版次備份_115102501_<時間>.json；同時寫本機 fy_qvf_bak_<qid>。
  3. saveQVersion(qid, q, {pre:true}) 存一份「還原前備份」（與 v6.0.148 同一套，永久保留）；saveQHistory() 回傳 false（空間滿）就取消。
  4. 寫 q.verFix 規則（含 before 原值，供復原）。
  5. 呼叫 _qhApplyFix(qid)：
  6. 新增正式版：{savedAt: SRC.savedAt+1, by, formal:true, ver:2, note, backfill:{fixId, src}, snapshot: 深拷貝(SRC.snapshot) 且 snapshot.ver=2}。依 savedAt 插到正確位置（不能用 unshift，否則 _qLastFormal 39934 會把它當成最新正式版，送出時的「內容相同不重複封存」就比錯版）。
  7. savedAt > shiftFrom、formal、ver ≥ 2 的每一筆：ver 與 snapshot.ver +1（目前只有那一筆 2→3）。
  8. q.ver = max(q.ver, verTo)。
  9. 改其他地方的版號（規則：舊號 ≥ 3 → +1；舊號 = 2 且建立時間晚於 SRC.savedAt → 3；其餘不變）：
  10. q.rfqs[].quoteVer（建立時間用 r.ts，沒有就 r.date）、r.chg.from／to、r.chgLog[]、q.costs[].chgLog[]，改完 r.mt=Date.now()。
  11. 這張報價的請款單 inv.quoteVer、it._qRetired，每張改完 _touch(inv)。
  12. 沒記 quoteVer 的舊詢價單不用改：rfqBaseVer 用建立時間推定，新版 2 的 savedAt 落在正確位置，推出來的號碼自然對。
  13. _touch(q)、persist()、saveQHistory()、_immediateUpload()。
  14. 草稿標已套用 _draftMark(id,'applied')、logActivity('報價','補登版次：115102501 V2（10/27）；原 V2→V3、編輯中 V3→V4')。
  15. 開「歷史版本」視窗給 Lotion 看結果。

冪等：_qhApplyFix 每次都照規則算「應該長怎樣」再改（新版已存在就不再加；號碼已經是新的就不再 +1——用 before.entries 記的原號判斷，不是看現值再 +1）。跑 1 次和跑 10 次結果一樣。

_qhApplyFix 要在這些地方都跑一次（這是要上程式的原因）：開頁讀本機後（27752 之後）、雲端合併後（10311 之後）、匯入備份後（5425）、私有資料補回後（10568）。有改到才 saveQHistory()。

復原（不加按鈕，主控台函式 qVerFixUndo(qid, fixId)，一樣先備份）：把規則標 undone:true、_touch(q)；_qhApplyFix 看到 undone 就把號碼照 before 還原、把補登那筆隱藏（不能真的刪：聯集合併會從別台裝置帶回來，所以用規則隱藏）、q.ver 還原（若之後又進版過，只扣回 1）。

  • 唯讀帳號（陳軒／HQ）在主控台跑 fyQuoteVerBackfill({qid, src: 16:34 那筆的 savedAt, ver:2, date:'2026-10-27', expect:{rows:18, sub:1758774, tax:87939, total:1846713}})，和 fyQuoteChange（40603）同一套：本機先試算、對不上就不送 → _draftPush('qverfix', payload, summary)。

3.4 風險與對策

#風險對策
1版次紀錄聯集合併：同一個 savedAt 本機優先（10003）。只改號碼的話，別台裝置保留舊號，而且 qHistory 是整包上傳，別台下一次存檔就把舊號傳回雲端蓋掉規則存在 q.verFix（報價記錄逐筆同步、_mt 新者勝，會傳到每一台），每台合併後都重跑 _qhApplyFix。程式要先上線、所有裝置重新整理兩次之後，才套用補登
2別台裝置還開著舊報價（q.ver=3）又存檔，q.ver 被打回 3_qhApplyFix 同時把 q.ver 補到 ≥ verTo（並 _touch）；套用時請 Lotion 確認其他裝置沒開著這張報價；套用後在第二台裝置驗收
3新版次用和來源同一個 savedAt，會被合併當成「同一筆」，別台永遠看不到 formal 旗標新版次用 SRC.savedAt+1，套用前檢查這個值沒被用過
4新版次的成本欄位（private）沒跟上只在私有資料已下載的管理員裝置套用（_QH_SENS!==null）；_qhSensMap 會從本機完整快照產生 qHistSens[qid][新 savedAt]
5待套用的 AI 改單草稿（baseVer=3）不改草稿。補登後 _qchgOpen 會顯示「草稿依據 V3，目前是 V4（V3 已封存）：會改在 V4」——這句剛好就是事實；另外會出現「草稿建立後這張報價被改過」，改單是逐列用說明文字對，對得上就能套。順序：先補登，再套 −30,000 改單，再送出
6補登前就先把 V4 送出了（又多封存一版）規則是「savedAt 晚於來源的正式版一律 +1」，多一版也照樣對；但建議先補登再送
7雲端每日提醒（functions/ops/todos.js）讀的是雲端那份 qHistory，舊裝置蓋回去的期間會誤報對策 1 生效後雲端會被改回；可選：把 _qhApplyFix 的純邏輯放 calc/（FJC），雲端讀 qHistory 後也套一次
8那筆 16:34 自動存檔被修剪掉目前程式沒有地方會再產生自動存檔，被擠掉的機率低，但「清理版本歷史」（cleanupQHistory）會只留 3 份。今天就先匯出全部資料備份，補登前不要按清理
9115110401 讓報價數／得標率多算一張第 5 節決定
10舊版程式的裝置（沒重新整理）不認得 verFix：顯示舊號、可能把舊號傳回雲端。新版裝置下一次合併就改回來；驗收前請每台都重新整理到新版

  2. 開 test.html（連 fj-system-test、鍵 test: 前綴，不會碰正式資料）→ 匯入剛剛的備份。
  3. 在測試專案用唯讀測試帳號跑 fyQuoteVerBackfill(...) 送卡片 → 管理員測試帳號套用。
  4. 驗：歷史版本清單 V1／V2（10/27）／V3（11/03）／現行 V4；三個數字；詢價單與請款單沒有冒出「未同步」提醒；改單草稿可套用、套用後含稅 1,826,213；送出並封存 → 出現 V4、編輯中變 V5。
  5. 第二個瀏覽器（模擬別台裝置，先載入舊資料、不重新整理）存一次檔 → 確認第一台再同步後號碼仍是對的（風險 1、2）。
  6. 跑一次 qVerFixUndo → 回到原狀；再套用一次 → 結果一樣（冪等）。
  7. 冒煙測試補：插入順序、冪等、聯集合併後重套、undo 隱藏、號碼對照規則、驗證不過不能套用、唯讀帳號不能套用。

4. 為什麼 V2 沒被封存，以及怎麼防

4.1 找到的漏洞（依可能性排）

#漏洞程式位置跟這次的關係
G110/27 當時根本沒有「送出並封存」：v6.0.158（commit 533e5c5，2026-11-03 14:13 UTC＝台灣 22:13）才有，之前要自己記得按「進版」—主因
G2舊版「還原」把目前內容存成一般自動存檔（非正式），所以 V2 只剩一筆非正式快照；現在的還原（v6.0.148 起）存成「還原前備份」，一樣不是正式版——如果目前內容已寄出但沒封存，還原時不會補封存restoreQVersion 2798611/03 16:34 那筆的由來；現在仍會再發生
G3「只匯出、不封存」完全不留紀錄，之後無從知道那份有寄出去_qSendGate 39958 _qSendOnly現在仍會發生
G4唯讀帳號（陳軒／HQ）匯出直接放行、不封存也不留紀錄_qSendGate 39948 if(_isReaderUser)return run(q)AI 代出 PDF 給業主時會發生
G5複製報價是一張全新的報價（_copyQDo 5813 刪掉 ver，新編號），送出複製品只會封存在複製品上，原報價的版次鏈看不到5807–5830115110401 就是這種「旁邊另建一張」的情況（而且是 11/04 建的）
G6在 FJ 以外送出（預覽畫面截圖傳 LINE、另存 Word 改完寄）系統不可能知道—只能事後抓
G7歷史版本視窗寫「每按一次儲存自動留一份（只留 10 份）」，但程式裡找不到存檔時呼叫 saveQVersion 的地方（只有進版 27808、還原 28000），所以實際上沒有這層安全網showQVersions 27963 文字說明文字跟實際不符（待確認）

4.2 修正提案（不加任何按鈕）

  1. 每次匯出都留紀錄：_qSendGate 所有出口（送出並封存／只匯出／內容相同／唯讀帳號）在 q.sendLog 記 {at, by, what, sig(雜湊), mode, ver}，最多 50 筆。「只匯出」另外把當下內容存成一筆 sent:true 的非正式紀錄（_qhKeep 把 sent 也算永久保留），內容不會再像 V2 一樣只能靠運氣找回來。
  2. 還原時自動補封存：restoreQVersion 檢查「目前內容」的簽章（_qSendSig 39933）是否等於某次匯出、但不等於任何正式版 → 確認視窗的文字改成「這份內容 10/27 匯出過、還沒封存，還原前會先封存成 V{n}」，按確認就先 _qBumpDo 再還原。只改既有視窗的文字與行為。
  3. 唯讀帳號匯出 → 送卡片：唯讀帳號不能寫入，所以匯出後自動 _draftPush('qsend', …)，Lotion 在 AI 草稿看到「陳軒匯出了 115102501（未稅 …）要封存嗎？」，套用＝封存。
  4. 健檢抓漏（前端 _healthRows 35388 加一項＋雲端 functions/ops/health.js）：
  5. 「匯出過、沒封存、內容已改掉」：sendLog 有 mode=only／reader 的紀錄，簽章不等於任何正式版也不等於現行 → 列出，點進去開第 3 節同一張「補登版次」卡片（補登工具因此變成通用功能，不只這一次用）。
  6. 「已得標，合約金額對不上任何正式版次或現行報價的含稅總計」→ 抓 G6（在 FJ 以外送出的版本）。
  7. 修正 G7 的說明文字（或補回存檔時的自動存檔，二選一，另案）。

5. 需要 Lotion 決定的

  1. V2 用哪一份當來源？

建議：用 11/03 16:34 那筆快照（它是原報價自己的紀錄，編號、業主、條款都是原本的），115110401 只拿來對照；再加上您手上 10/27 寄給業主的 PDF，三份一致才補登。三個數字對不上就停，不硬補。

  1. 115110401（第二份報價，未採用）補登完要怎麼處理？

建議：補登驗收完刪掉（走一般刪除，會進回收筒，可救回）。留著的話，報價張數、得標率會多算一張未得標。不想刪就至少改名「（已併入 115102501 V2）」並標未得標。

  1. 「只匯出、不封存」要不要留？

建議：留，但照 4.2 每次匯出都留紀錄＋健檢提醒，自己看的時候不會多出一堆版次。另一個選擇是拿掉、一律封存：最不會漏，但只是自己看一下也會多一版。
